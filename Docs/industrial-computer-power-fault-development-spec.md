# 工控机供电故障与多案例驱动开发 Spec

> 版本：V1.1（工程约束补充稿，待确认）
> 日期：2026-07-26
> 开发分支：`feature/industrial-computer-power-fault`
> 当前阶段：开发方案复审完成，尚未编写业务代码
> 首个新增故障：工控机 24V DC 供电路径异常 / 启动欠压
> 首个演示设备：Rockwell ASEM 6300B-EW1 Box PC
> 新案例 ID：`CASE-ROCKWELL-6300-002`
> 候选知识 ID：`KB-ROCKWELL-6300-POWER-001`

## 1. 文档目的

本 Spec 用于规定“第二个正式故障”应该如何接入现有系统，并同时解决当前系统过度绑定散热案例的问题。

用户已经确认最终产品形态不是只支持散热和供电两个固定页面，而是：

> 预先准备若干个内容完整的故障案例 JSON。工程师在首页输入现场描述后，系统根据设备、告警、现象和关键测量进行案例路由，再进入该故障专用的一整套诊断、检修、作业卡、专家审核、知识和图谱链路。

系统在演示中呈现为能够根据现场输入生成不同处理链路；当前版本的实现基础则是经过人工编排、手册核实和验收的有限案例库。新增案例需要增加数据包和必要的专用视觉内容，不应重新复制整套页面。

本轮不是简单增加一张案例卡，也不是把散热页面中的文字替换成供电故障。目标是建立一层可复用的案例驱动结构，使以下内容都能根据 `caseId` 读取不同 JSON 配置：

```text
异常接入
→ 诊断依据与多 Agent 会诊
→ 可编辑检修预方案
→ 逐步检修向导
→ 检修智能体步骤问答
→ 检修记录
→ 两页打印作业卡
→ 专家审核
→ 知识发布
→ 知识图谱增量
→ 工程师知识同步
```

本 Spec 通过后，后续开发只能按这里规定的数据边界、实施批次和验收条件推进。若开发过程中需要改变案例范围、可信等级或演示主线，应先更新本 Spec，再修改代码。

### 1.2 V1.1 工程补充的效力

V1.1 在不改变“双案例演示、JSON 驱动、供电故障为第二案例”产品方向的前提下，补充了可落地的工程约束。第 19～29 节是对前文的细化；如与 V1.0 原描述存在冲突，以第 19～29 节为准。

本次复审重点解决：

- 案例模板与一次实际演示运行混在一起；
- 单个巨型 JSON 难以维护、校验和评审；
- 路由缺少明确阈值、歧义处理和服务端权威结果；
- 当前 SQLite 初始化方式不能可靠迁移已有演示库；
- 专家发布、作业卡和图谱缺少不可变快照与版本边界；
- 前端只替换文字、不替换状态模型时容易发生跨案例串数据；
- 可信度只挂在案例顶层，无法证明每条结论和操作的来源；
- 只用两个正式案例无法证明第三个案例真的可以“只加数据、不改页面”。

### 1.1 已确认的产品目标

```text
首页自然语言输入
→ 识别设备、故障域、告警和关键现象
→ 从预置案例注册表计算候选案例
→ 工程师确认故障方向
→ 加载对应案例 JSON
→ 运行该案例完整业务链路
```

系统第一阶段至少包括：

1. 散热异常完整案例；
2. 24V DC 供电路径异常完整案例。

系统结构必须允许后续继续加入：

- POST / UEFI 启动异常；
- HDD/SSD 存储与镜像恢复；
- 显示异常；
- RTC 电池异常；
- 系统监控与远程告警；
- 通信接口与外设异常；
- 其他资料成熟并通过验收的工控机故障。

这些后续故障不在当前供电分支中同时开发，但本轮数据结构和路由层必须为它们保留统一接入方式。

## 2. 当前项目基线

### 2.1 已有完整能力

当前系统已经具备：

- 工程师、专家、管理员三种演示身份；
- 动态异常接入与现场材料预览；
- 设备、告警和运行参数确认；
- 多 Agent 会诊演示；
- 可编辑的两级检修预方案；
- 逐步检修向导；
- 检修步骤内上下文问答；
- 检修完成记录与两页打印作业卡；
- 工程师上传、专家审核和知识发布；
- SQLite 持久化；
- 全局知识图谱与“本次新增与修改”；
- 工程师本地知识同步；
- 15 份官方手册、17 条知识和约 56 个图谱节点。

### 2.2 当前唯一完整案例

目前只有以下案例真正贯穿完整链路：

```text
CASE-ACP4000-001
→ ACP-4000 / IPC-610 散热异常
→ KB-008 V1.0 → V1.1
→ 风扇老化、转速低、告警解除等图谱增量
```

### 2.3 当前结构性问题

现有代码和状态仍大量硬编码散热字段：

- `CASE-ACP4000-001`；
- `KB-008`；
- TEMP/FAN 告警；
- 风扇转速、系统温度、CPU 温度；
- 风道、滤网、风扇和 FAN1/FAN2；
- 散热专用检修步骤；
- 散热专用工程师结果字段；
- 散热专用作业卡指标；
- 散热专用专家结论和图谱变更；
- SQLite 中单一 `presentation_state`。

因此，供电故障不能通过“再加几个 if”完成。若继续直接在页面里堆条件，第三个故障会再次复制全部流程，最终难以维护和演示。

## 3. 新故障定义

### 3.1 页面通用名称

面向产品界面和演示讲解，统一使用：

> 工控机供电异常

不在一级页面标题中反复突出品牌和完整型号。

### 3.2 案例具体设备

案例详情、手册依据、参数和端子说明必须明确：

> Rockwell ASEM 6300B-EW1 Box PC

选择单一型号的原因：

- 6300B-EW1 的最大功耗为 60W；
- 6300P-EW1 的最大功耗为 85W；
- 两种设备的形态和现场角色不同；
- 同时展示两个型号会造成参数、图片和检修对象混乱。

### 3.3 故障边界

本案例只处理：

- Power LED 熄灭；
- 无法稳定上电；
- 启动过程中掉电；
- 设备端启动电压低于官方工作范围；
- 中间供电路径或 Power DC Connector 接线异常；
- DC 端子松动、接触不良或缺少应力释放；
- 供电异常引起的非正常关机风险。

本案例不处理：

- TEMP/FAN 或散热异常；
- 显示屏本体故障；
- RTC 电池故障；
- SSD/HDD 本体故障；
- 网络通信故障；
- 主板内部电源电路维修；
- 其他型号的端子针脚或额定参数。

### 3.4 冻结演示事实

第一版开发采用现有结构化文档中的冻结数据：

## 4. 演示定位与可信度规则

### 4.1 第一版可以演示什么

第一版可以完整演示：

- 系统识别供电异常方向；
- 根据官方手册判断 11.6V 低于 18V 下限；
- 区分“上游模块正常”和“设备端供电正常”；
- 形成供电路径原因树；
- 生成供电专用检修预方案；
- 引导测量、断电、端子处理和恢复验证；
- 生成供电故障作业卡；
- 由专家修正诊断结论；
- 形成候选知识和图谱增量；
- 工程师同步后命中供电知识。

### 4.2 第一版不能声称什么

由于当前缺少真实现场照片、铭牌、测量记录和真实专家签字，页面不得声称：

- 这是已核实的真实场站工单；
- DC-端子松动已经由真实现场证据确认；
- 11.6V 和 23.7V 是真实仪表测量；
- 案例已经达到 `verified_case`；
- 专家审核演示能把构造数据变成真实现场事实。

### 4.3 统一可信度字段

后续数据统一使用：

| 字段值 | 含义 |
| --- | --- |
| `official_document` | 厂家官方手册中已经核实 |
| `synthetic_demo` | 为页面、视频和流程验证构造的演示事实 |
| `field_evidence` | 来自真实现场照片、测量、日志或工单 |
| `expert_confirmed` | 专家确认的项目规则或专业结论 |
| `verified_case` | 真实现场证据和专家审核共同支持 |

专家审核构造案例后：

- `reviewStatus` 可以变为 `expert_reviewed`；
- `verificationLevel` 仍保持 `synthetic_demo`；
- 只有补齐真实现场证据后才能升级为 `verified_case`。

## 5. 总体技术方案

### 5.1 核心原则

采用：

> 案例注册表 + 模块化 JSON 案例包 + 服务端路由 + SQLite CaseRun

职责划分：

```text
JSON
├── 保存稳定的案例内容、判据、步骤、文案、知识候选和图谱候选
└── 作为演示重置种子和离线兜底

SQLite
├── 保存工程师执行结果
├── 保存专家草稿与审核结果
├── 保存发布的知识版本
├── 保存发布的图谱增量
└── 保存工程师本地同步状态

React
├── 根据 CaseSession 中的 caseId、runId 和 stage 渲染当前内容
├── 管理当前页面交互与动画
└── 不再直接保存每个案例的大量业务常量

Flask
├── 读取和校验案例包
├── 根据 runId 返回当前阶段允许的诊断、步骤和记录
├── 提供兼容旧接口的默认案例
└── 调用 SQLite 完成动态状态事务
```

### 5.2 不采用的方案

第一版不采用：

- 为供电故障复制一套独立 React 应用；
- 在 `App.jsx` 中继续增加大量品牌和故障 `if/else`；
- 每个页面自行保存一份案例常量；
- 将整本 PDF 转成 JSON；
- 引入图数据库；
- 引入新的前端图谱依赖；
- 接入真实大模型或向量检索；
- 把所有历史摘要案例都升级为完整案例。

### 5.3 已确认的演示实现方式

演示采用“有限案例库 + 输入路由”，不采用无限开放式生成。

每个允许进入主流程的故障都必须具备：

- 可识别的首页输入规则；
- 一组设备、告警和现场现象字段；
- 专用诊断结论和证据链；
- 专用检修预方案；
- 专用检修向导；
- 当前步骤可用的问答主题；
- 专用工程师结果字段；
- 专用两页作业卡；
- 专家审核内容；
- 知识候选；
- 图谱候选；
- 来源和可信度；
- 完整自动化与浏览器验收。

只有案例摘要、手册或几条图谱节点的故障不能出现在首页主流程候选中。它们继续作为知识库和全局图谱内容展示。

## 6. 案例 JSON 设计

### 6.1 建议目录

```text
backend/data/cases/
├── case_registry.json
├── schemas/
│   ├── registry.schema.json
│   ├── manifest.schema.json
│   ├── intake.schema.json
│   ├── diagnosis.schema.json
│   ├── guide.schema.json
│   ├── assistant.schema.json
│   └── output.schema.json
├── CASE-ACP4000-001/
│   ├── manifest.json
│   ├── intake.json
│   ├── diagnosis.json
│   ├── guide.json
│   ├── assistant.json
│   ├── output.json
│   └── feedback-and-graph.json
├── CASE-ROCKWELL-6300-002/
│   └── ...  # 使用同一模块结构
└── CASE-FIXTURE-003/
    └── ...  # 仅用于证明第三案例无需改页面代码
```

继续保留：

```text
backend/data/presentation/
├── manual_sources.json
├── knowledge_base.json
├── industrial_computer_graph.json
└── presentation.db
```

说明：

- 每个完整案例使用一个目录化、可组合的案例包，`manifest.json` 是入口；
- 手册、全局知识和全局图谱仍是共享资源；
- 案例包只引用手册 ID、知识 ID 和图谱节点 ID，不复制整本知识库；
- 历史只读摘要继续留在 `cases.json` 或后续迁入注册表。
- 加载器对外仍返回一个统一 CasePackage DTO，因此前端不感知文件拆分；
- 所有引用路径必须限制在当前案例目录内，禁止 `..`、绝对路径和符号链接逃逸。

### 6.2 案例注册表

`case_registry.json` 负责告诉系统有哪些案例、每个案例是否允许进入完整流程，以及首页输入如何匹配到该案例。

建议字段：

```json
{
  "registryVersion": "1.1",
  "items": [
    {
      "id": "CASE-ACP4000-001",
      "package": "CASE-ACP4000-001/manifest.json",
      "mode": "interactive",
      "faultCode": "industrial-computer-cooling",
      "matchRules": {
        "equipment": ["ACP-4000", "IPC-610", "研华工控机"],
        "alarms": ["TEMP/FAN", "蜂鸣"],
        "symptoms": ["温度升高", "风扇低速", "风扇异响", "滤网积尘"],
        "exclusions": ["Power LED不亮", "24V启动欠压"]
      }
    },
    {
      "id": "CASE-ROCKWELL-6300-002",
      "package": "CASE-ROCKWELL-6300-002/manifest.json",
      "mode": "interactive_demo",
      "faultCode": "industrial-computer-power",
      "matchRules": {
        "equipment": ["6300B-EW1", "Rockwell工控机"],
        "alarms": ["Power LED OFF", "Power LED不亮"],
        "symptoms": ["无法上电", "启动掉电", "反复重启", "24V欠压"],
        "measurements": ["设备端低于18V", "上游正常设备端异常"],
        "exclusions": ["TEMP/FAN", "散热异常"]
      }
    }
  ]
}
```

注册表只保存路由所需的轻量字段。案例标题、可信等级和设备身份等权威内容只存在于案例包；注册表不得复制这些字段。启动校验需确认注册表 ID 与 `manifest.identity.caseId` 一致，并记录 `registryVersion`、案例包版本和内容哈希。

### 6.5 `provenance`

负责区分官方事实与演示事实：

```json
{
  "verificationLevel": "synthetic_demo",
  "reviewStatus": "unreviewed",
  "officialSources": [
    {
      "documentId": "DOC-ROCKWELL-6300-UM003B",
      "pages": [25, 37, 39, 43, 48, 70, 79]
    }
  ],
  "limitations": [
    "现场测量数据为演示构造",
    "尚未取得真实铭牌和处理前后照片"
  ]
}
```

### 6.6 `intake`

负责首页输入、接诊任务和字段：

- 默认异常描述；
- 推荐设备型号；
- 关联告警；
- Power LED；
- 上游输出电压；
- 设备端静态电压；
- 设备端启动最低电压；
- DC 端子状态；
- POST 状态；
- Windows 和业务软件状态；
- 每个字段的来源；
- 页面展示顺序；
- 分支识别关键词。

供电案例不再显示：

- TEMP/FAN；
- 风扇 rpm；
- 系统温度；
- CPU 温度。

### 6.7 `diagnosis`

负责：

- 诊断方向；
- 原因排序；
- 证据链；
- 多 Agent 名称、输入、思考文本、来源和结论；
- 风险等级；
- 排除项；
- 是否允许进入检修；
- 需要升级厂家支持的条件。

供电诊断主逻辑：

```text
Power LED OFF
＋ 上游启动瞬间 23.9V
＋ 设备端启动瞬间 11.6V
＋ 中间端子排输出波动
＋ DC-端子松动
→ 上游模块正常但中间供电路径存在严重压降
→ 优先处理端子与接线工艺
→ 不直接判断主板损坏
```

### 6.8 `maintenancePlan`

负责可编辑预方案的系统初稿。

供电案例建议分为五个大步骤：

1. 保存故障原状并确认作业边界；
2. 分段测量供电路径并核算容量；
3. 正常关机、断电并检查 DC 接线；
4. 修复端子、极性和应力释放；
5. 恢复供电并验证系统与业务。

必须锁定的安全项：

- 通知值班负责人；
- 由具备资质人员执行带电测量；
- 禁止带电拆装端子；
- 正常关机；
- 断开上游电源和外设；
- 防静电；
- 烧蚀、发热、变形或异味时立即停止。

### 6.9 `guide`

每个向导步骤至少包含：

```json
{
  "id": "step-power-02-measure",
  "title": "分段测量供电路径",
  "description": "比较上游、电源端子排和设备端启动瞬间电压",
  "checks": [],
  "measurements": [],
  "safety": [],
  "thresholds": [],
  "visuals": [],
  "assistantTopics": [],
  "completionCriteria": []
}
```

检修向导的 15 个具体操作项应归入五个大步骤，而不是在左侧流程中铺成 15 个同级页面。

### 6.10 `assistant`

案例包声明可用知识主题，问答实现不直接判断页面标题。

供电案例第一版知识主题：

| 主题 ID | 可回答内容 |
| --- | --- |
| `power-voltage-range` | 为什么 11.6V 异常、18～32V 的来源 |
| `power-path-isolation` | 上游 24V 正常为什么设备仍不上电 |
| `power-capacity` | 60W、120W 和容量余量如何判断 |
| `power-connector-pins` | Pin 1 +24V、Pin 2 0V |
| `power-terminal-workmanship` | 线径、7mm 剥线和端子力矩 |
| `power-led-status` | OFF、绿色常亮、绿色闪烁、绿色渐变 |
| `power-shutdown-safety` | 为什么不能直接断电或优先按 Reset |
| `power-recovery` | POST、Windows、日志和业务恢复标准 |

每个步骤只开放与本步相关的主题。例如：

- 测量步骤开放电压范围、供电路径和容量；
- 端子步骤开放针脚、线径、剥线和力矩；
- 恢复步骤开放 LED、POST、日志和观察时间。

### 6.11 `engineerResult`

不同案例使用不同指标，但保持公共字段：

```json
{
  "commonFields": [
    "finalCause",
    "actualResolution",
    "recoveryResult",
    "observationMinutes",
    "residualRisk"
  ],
  "metrics": [
    "upstreamVoltageBefore",
    "deviceVoltageBefore",
    "deviceVoltageAfter",
    "startupMinimumAfter"
  ]
}
```

前端不能再固定读取 `fanSpeedRpm`、`systemTemperatureC` 和 `cpuTemperatureC`。

### 6.12 `jobCard`

作业卡继续保持两页。

第一页：

- 设备与故障摘要；
- 风险等级；
- 核心诊断结论；
- 官方判据；
- 处理前测量；
- 供电路径定位结果；
- 安全前置条件。

第二页：

- 实际处理摘要；
- 端子工艺参数；
- 处理前后指标对比；
- Power LED、POST、Windows 和业务恢复；
- 观察结果；
- 遗留风险；
- 工程师和专家签字位置；
- 数据来源标识。

作业卡只保留可打印的关键检修内容，不复制右侧 Agent 思考过程。

### 6.13 `knowledgeProposal`

V1.0：

- 只包含官方手册知识；
- 验证等级为 `official_document`；
- 可用于现场判据、针脚、力矩和安全要求。

V1.1 候选：

- 增加“上游正常不能排除设备端路径异常”；
- 增加分段动态测量经验；
- 增加 DC-端子松动与启动压降关系；
- 数据来源为 `synthetic_demo`；
- 专家审核后仍不能自动变成 `verified_case`。

### 6.14 `graphProposal`

第一版候选增量至少包括：

```text
6300B-EW1 → 工作电压范围 → 18～32V DC
DC-端子松动 → 导致 → 启动负载压降
启动瞬间 11.6V → 低于 → 18V 工作下限
启动负载压降 → 导致 → Power LED OFF
启动负载压降 → 导致 → POST 无法开始
复紧并重做 DC 端头 → 修复 → 设备端供电路径
设备端 24.0V → 支持 → 供电恢复
Power LED 绿色常亮 → 指示 → 系统由输入电源供电
CASE-ROCKWELL-6300-002 → 来源于 → 演示构造案例
```

图谱节点必须保留：

- `verificationLevel`；
- `sourceRefs`；
- `sourceCaseIds`；
- `knowledgeId`；
- `changeType`；
- `status`。

## 7. 多案例运行时设计

### 7.1 前端状态

新增统一的 `CaseSession`，由 reducer 或等价状态仓库管理：

```text
sessionId
runId
caseId
routeStatus
stage
runStatus
dataRevision
activeStepId
pendingRequestIds
intakeSessionId
```

各页面只能从当前案例包或运行状态读取内容，不允许直接引用散热常量。切换案例或运行实例时必须取消旧请求和计时器；无法取消的旧响应必须通过 `sessionId + runId + dataRevision` 判定并丢弃。

### 7.2 案例识别

第一版支持两种入口：

1. 首页描述触发关键词与设备匹配；
2. 开发和录制时提供不抢主线的“采用演示案例”入口。

正式演示优先使用自然语言输入。演示案例入口只用于开发、验收和录制兜底，不作为主讲解方式。

#### 7.2.1 路由输入

案例路由使用首页和异常接入阶段已经获得的信息：

- 用户原始描述；
- 设备型号；
- 设备角色；
- 关联告警；
- 图片或视频的人工确认标签；
- 运行参数；
- 当前场站与柜位；
- 用户后续修正。

当前版本不声称真实理解图片内容。图片标签来自预置演示或工程师确认。

#### 7.2.2 路由评分

建议采用可解释的规则评分，而不是在前端散落布尔判断：

| 命中项 | 建议分值 |
| --- | ---: |
| 完整设备型号 | +50 |
| 同系列或通用设备名称 | +25 |
| 核心告警 | +30 |
| 核心故障现象 | 每项 +10 |
| 关键测量判据 | +25 |
| 场景或设备角色 | +5 |
| 明确排除项 | -100 |

示例：

```text
ACP-4000 / IPC-610 + TEMP/FAN / 温度 / 风扇
→ CASE-ACP4000-001

6300B-EW1 + Power LED / 24V / 不上电 / 启动掉电
→ CASE-ROCKWELL-6300-002
```

#### 7.2.3 路由结果

路由结果分为：

| 状态 | 页面行为 |
| --- | --- |
| `matched` | 一个案例明显领先，展示识别结果并让工程师确认 |
| `ambiguous` | 两个案例分数接近，展示最多两个候选方向供工程师选择 |
| `insufficient` | 信息不足，继续询问设备、告警或关键测量 |
| `unsupported` | 没有完整案例支持，进入通用知识建议，不得误入散热案例 |

系统识别后必须由工程师确认设备和故障方向，不能自动替代最终确认。

#### 7.2.4 输入触发示例

散热异常：

> 站控柜A01工控机出现TEMP/FAN告警，风扇声音异常，转速只有420rpm，系统温度持续升高。

供电异常：

> 站控柜B02的Rockwell 6300B工控机Power LED不亮，24V电源模块显示正常，但设备启动一下又掉电。

系统不要求用户逐字输入固定提示词。相同含义的“上不了电”“开机掉电”“电源灯不亮”“设备端只有11.6V”等表达应由同一组意图规则覆盖。

### 7.3 案例切换规则

- 切换案例时清空当前步骤、勾选项和临时对话；
- 上传材料先绑定 `intakeSessionId`；工程师确认案例后再显式关联到新建的 `runId`；
- 切换案例时不得默认携带已上传材料，必须由工程师确认复用；
- 不把散热步骤进度带入供电案例；
- 当前案例 ID 必须写入诊断请求、检修记录和专家提交；
- 页面刷新后从 SQLite 或会话状态恢复当前案例。

### 7.4 未支持故障的处理

如果用户输入的故障只有手册知识但没有完整案例包，例如 RTC 电池异常：

- 可以展示命中的知识库条目；
- 可以展示全局图谱中的相关节点；
- 可以提供基础安全提醒；
- 可以提示“当前尚未生成完整检修案例链路”；
- 不得伪装成已具备完整诊断、向导和知识回流；
- 不得默认跳到散热异常。

这样既能保持系统看起来具有较丰富的知识覆盖，也能明确区分“完整可演示案例”和“只有知识支持的故障”。

### 7.5 后续新增案例的标准动作

以后每新增一个完整故障，开发流程固定为：

```text
选择材料成熟的故障
→ 冻结设备和故障边界
→ 建立案例 JSON
→ 在注册表加入 matchRules
→ 校验手册与知识引用
→ 完成专用诊断和向导内容
→ 完成作业卡、专家和图谱候选
→ 自动化测试
→ 浏览器完整链路验收
→ 才允许进入首页路由
```

理想情况下，第三个案例开始主要增加 JSON、专用图片和少量新问答意图，不再修改整套页面状态机。

## 9. SQLite 多案例状态规划

### 9.1 现状

现有：

- `cases` 表本身支持多个案例；
- `knowledge_items`、`knowledge_versions` 支持多个知识；
- `graph_nodes`、`graph_relations` 支持多个知识版本；
- `engineer_sync_records` 支持不同知识；
- 但 `presentation_state` 仍是单一全局 payload；
- 初始化和发布逻辑默认只处理一个动态案例和一个动态知识。

### 9.2 调整方案

保留 `presentation_state` 保存：

- 当前角色；
- 当前激活案例；
- 全局演示设置；
- 最近操作时间。

新增：

```text
case_runs
├── run_id                 # 主键；一次演示或一次检修一个实例
├── case_id
├── package_version
├── package_hash
├── status
├── revision
├── payload
├── created_by
├── created_at
└── updated_at
```

每个运行实例独立保存：

- 工程师是否确认；
- 当前检修进度；
- 工程师结果；
- 专家草稿；
- 图谱决策；
- 知识发布状态；
- 当前知识版本；
- 演示可信度。

### 9.3 发布事务

发布接口必须显式接收：

```text
caseId
runId
knowledgeId
verificationLevel
expectedCurrentVersion
expectedRevision
idempotencyKey
```

服务端依据当前版本计算下一个知识版本，不接受客户端指定 `targetVersion`，不得再固定发布 `KB-008 V1.1`。

供电案例发布后：

- 允许知识版本进入 SQLite；
- 允许图谱增量进入“本次新增与修改”；
- 必须显示 `synthetic_demo`；
- 不得覆盖散热案例的同步状态；
- 工程师按知识 ID 分别同步 `KB-008` 和供电知识。

## 19. 核心领域模型与数据权威

### 19.1 四类对象不得混用

| 对象 | 含义 | 是否可变 | 权威存储 |
| --- | --- | --- | --- |
| `CasePackage` | 经编排的案例模板 | 发布后不可变 | JSON 文件 |
| `CaseRun` | 一次工程师演示或检修实例 | 状态机内可变 | SQLite |
| `KnowledgeVersion` | 专家审核后形成的知识版本 | 每个版本不可变 | SQLite |
| `GraphVersionDelta` | 某知识版本对应的图谱增量 | 每个版本不可变 | SQLite |

`caseId` 标识案例类型，不能标识一次执行。所有会变化的进度、回答、测量、工程师修改和专家意见必须挂在 `runId` 下。

### 19.2 数据权威规则

- JSON 案例包是模板、初始内容和路由规则的权威来源；
- SQLite 是运行实例、审核意见、发布版本和同步记录的权威来源；
- 全局知识图谱由“基线图谱 JSON + SQLite 当前已发布版本”合成；
- “本次新增与修改”必须按 `runId + caseId + knowledgeId + version` 查询；
- 注册表只是路由索引，不是案例内容的第二份权威数据；
- 运行开始时固化 `packageVersion + packageHash`，后续修改 JSON 不影响历史运行；
- 历史作业卡、审核记录和发布记录不得使用最新 JSON 重新计算。

### 19.3 完整数据血缘

```text
不可变案例包
→ CaseRun.resolvedPlanSnapshot
→ stepExecution / measurements / assistantMessages
→ engineerSubmissionSnapshot
→ jobCardSnapshot
→ expertReviewSnapshot
→ KnowledgeVersion
→ GraphVersionDelta
→ EngineerSyncRecord
```

每一层保存上一层的标识、版本、内容哈希和生成时间。下游只能从已固化的上游快照生成，不能越级回读当前模板。

## 20. 案例包 Schema 与加载契约

### 20.1 模块职责

| 文件 | 必须包含 |
| --- | --- |
| `manifest.json` | Schema 版本、案例身份、包版本、模块引用、来源摘要、能力声明 |
| `intake.json` | 输入字段、字段类型、单位、必填条件、路由事实映射 |
| `diagnosis.json` | 诊断方向、证据规则、Agent 展示、结论条件、升级条件 |
| `guide.json` | 计划、步骤、检查项、测量项、安全项、视觉内容、完成条件 |
| `assistant.json` | 主题、意图、同义表达、回答、来源、安全与适用步骤 |
| `output.json` | 工程师结果字段、记录模板、作业卡区块、专家审核表单 |
| `feedback-and-graph.json` | 知识候选、图谱候选、发布映射和同步摘要 |

加载器只有在所有模块通过校验后才能返回 CasePackage。任一必需模块缺失、Schema 不支持、引用断裂或路径越界时，案例必须 `fail closed`，不得进入首页可选列表。

### 20.2 可执行 JSON Schema 要求

开发阶段必须提交真实的 JSON Schema 文件，而不是只写 TypeScript/Python 类型。每个 Schema 至少规定：

- `$schema`、`$id`、`schemaVersion`；
- `required`、`type`、`enum`、`pattern`；
- 默认 `additionalProperties: false`；
- ID 格式和同一模块内唯一性；
- 支持的版本范围及不兼容版本错误；
- 字段长度、数字范围和单位枚举；
- 跨模块引用的目标类型。

启动校验还必须覆盖 JSON Schema 无法单独完成的约束：

- 所有 `stepId`、`checkId`、`topicId`、`sourceRef` 均存在；
- `allowedStepIds` 指向有效步骤；
- 检查项 ID 在案例包版本内稳定，不得用显示文本充当 ID；
- 图谱边的起止节点存在；
- 知识和图谱候选引用同一个 `knowledgeId`；
- 注册表 ID、manifest ID 和目录名一致；
- 包内引用不得逃逸案例目录。

### 20.3 Schema 版本策略

- 当前只实现 `1.1.x`；
- 补丁版本允许增加可选字段；
- 次版本升级必须提供迁移器或同时支持旧版本；
- 主版本不兼容时拒绝加载并给出明确错误；
- CI 对所有正式案例和测试夹具执行加载与引用完整性校验。

### 20.4 事实、证据和可信度

顶层单一 `verificationLevel` 不足以表达混合来源。所有可影响判断或输出的 claim 必须支持：

```json
{
  "claimId": "claim-power-input-range",
  "sourceType": "official_manual",
  "verificationStatus": "source_verified",
  "reviewStatus": "reviewed",
  "evidenceRefs": [
    {
      "documentId": "DOC-ROCKWELL-6300-UM003B",
      "pages": [37],
      "locator": "Power input specification"
    }
  ]
}
```

以下内容必须逐条关联 claim 或 evidence：

- 测量值和阈值；
- 诊断结论与排除项；
- 检修操作与安全要求；
- 智能体回答；
- 作业卡判据；
- 知识条目；
- 图谱节点和关系。

`sourceType` 表示来源类型，`verificationStatus` 表示证据核实状态，`reviewStatus` 表示人工审核状态，三者不可合并。`synthetic_demo` 经专家审核后仍是演示数据，不自动升级为真实案例。实施前必须重新审计散热案例的 `verified_case` 标识；无法提供真实案例证据时降为准确的可信等级。

## 21. 案例路由协议

### 21.1 服务端为唯一权威路由器

前端只收集事实和展示解释，不自行决定 `caseId`。统一接口：

```text
POST /api/demo/case-routing
```

请求包含 `intakeSessionId`、原始描述、结构化设备信息、告警、人工确认标签和测量。服务端依次执行：

```text
文本规范化
→ 型号/告警/单位标准化
→ 同义词与宽松意图识别
→ 否定词和排除项识别
→ 硬性门槛
→ 加权评分
→ 最低分与领先差值判断
→ 返回候选、证据和缺失信息
```

### 21.2 返回状态和确定性

| 状态 | 条件 | 行为 |
| --- | --- | --- |
| `matched` | 最高分达到 `minScore` 且领先达到 `minMargin` | 展示一个方向，等待确认 |
| `ambiguous` | 多个候选达标但领先不足 | 最多展示两个候选 |
| `insufficient` | 缺少设备、告警或关键判据 | 返回下一条追问 |
| `unsupported` | 明确不属于完整案例或均未达标 | 只进入通用知识支持 |

具体 `minScore`、`minMargin` 和权重必须存在于可测试配置中。相同输入、注册表版本和算法版本必须产生相同结果；同分时按明确的稳定规则排序。响应至少返回：

```json
{
  "routeStatus": "matched",
  "routingAlgorithmVersion": "1.0",
  "registryVersion": "1.1",
  "candidates": [
    {
      "caseId": "CASE-ROCKWELL-6300-002",
      "score": 115,
      "matchedFacts": [],
      "excludedFacts": [],
      "missingFacts": []
    }
  ]
}
```

只有工程师确认候选后，`POST /api/demo/case-runs` 才创建 `runId`。`defaultCaseId` 只允许用于显式 legacy/dev 模式，正常演示绝不静默兜底。

### 21.3 路由测试语料

建立版本化 golden corpus，至少覆盖：

- 标准表述、口语、错别字和缩写；
- “怎么接”“先接哪个”“这个顺序怎么样”等同义意图；
- 中文/英文型号和告警；
- `11.6V`、`11.6 V`、`11600mV` 等单位变体；
- “没有 TEMP/FAN 告警”等否定表达；
- 同时出现供电和温升信号的冲突输入；
- 信息不足和系统未支持故障；
- 恶意超长输入和未知字段。

## 22. CaseRun 状态机与并发控制

### 22.1 状态机

```text
created
→ intake_confirmed
→ diagnosed
→ plan_confirmed
→ in_progress
→ engineer_submitted
→ expert_reviewing
→ approved | rejected
→ published
→ synced
```

允许 `rejected → in_progress` 返工；`published` 后运行快照只读。每个写接口在后端校验允许的前置状态，不能只靠前端禁用按钮。

### 22.2 写入协议

所有改变状态的接口必须携带：

- `runId`；
- `expectedRevision`；
- `idempotencyKey`。

事务成功后 `revision + 1`。版本不一致返回 `409 state_conflict` 并携带当前 revision；重复 `idempotencyKey` 返回第一次成功结果，不重复完成步骤、生成版本或插入图谱。

### 22.3 计划和执行记录

工程师确认预方案时生成 `resolvedPlanSnapshot`。向导只读取该快照，不继续读取模板的 `maintenancePlan`。执行记录至少保存：

- 稳定的 `stepId`、`checkId`、`measurementId`；
- 实际值、单位、操作者和时间；
- 跳过原因、异常说明和附件引用；
- 使用的 claim/evidence 版本；
- 完成时的 revision。

安全项同时由 Schema、服务端状态转换和记录生成校验。锁定安全项不得被前端删除或绕过。

### 22.4 重置范围

提供三种明确操作，不允许一个 reset 删除所有数据：

1. `reset run`：只重置指定 `runId` 的未发布运行数据；
2. `reset case demo`：新建该案例的干净运行，不删除历史 run；
3. `reset all demo data`：仅管理员开发模式可用，需二次确认和备份。

已发布知识、图谱版本、专家审核和同步记录不随运行重置删除。

## 23. 数据库迁移、初始化与恢复

### 23.1 迁移机制

新增 `schema_migrations` 表，按顺序执行幂等迁移。不得继续以“某张表是否存在”判断是否重建整个数据库。每次迁移必须：

1. 检查当前 schema 版本；
2. 备份 `presentation.db`；
3. 在事务中执行 DDL、数据迁移和索引创建；
4. 校验关键表、外键和种子数据；
5. 失败则回滚并保留备份；
6. 记录迁移版本、时间和校验结果。

### 23.2 种子数据协调

- Seed 只补充缺失的基础手册、案例摘要、知识和图谱基线；
- 不覆盖专家修改、已发布版本、运行实例或同步状态；
- Seed ID 冲突但内容哈希不一致时中止并报告；
- 案例包启动加载失败时不修改现有数据库；
- CI 使用空库验证全量初始化，再使用 V1.0 样例库验证升级迁移。

### 23.3 建议新增表

```text
schema_migrations
case_runs
case_run_events
case_run_idempotency
case_run_attachments
engineer_submission_snapshots
job_card_snapshots
expert_review_snapshots
```

表结构设计应保留现有知识和图谱表，优先用外键或显式校验关联 `runId`、`caseId`、`knowledgeId` 和版本。迁移设计完成前不编写业务页面。

## 24. API、权限与响应裁剪

### 24.1 不提前泄露答案

完整 CasePackage 仅供后端加载。前端接口必须按角色和阶段返回 DTO：

- 接诊阶段：身份、输入字段和可公开提示；
- 诊断阶段：当前可见证据、Agent 展示和待确认结论；
- 向导阶段：当前步骤及允许的相邻导航信息；
- 工程师提交后：工程师总结和候选知识；
- 专家阶段：完整证据、工程师快照和审核表单。

未到阶段时不能通过抓取 `/api/demo/cases/<case_id>` 得到最终原因、恢复值、专家答案或图谱发布结论。

### 24.2 错误契约

接口统一返回稳定错误码：

| HTTP | code | 场景 |
| ---: | --- | --- |
| 400 | `validation_error` | 请求字段或单位无效 |
| 404 | `case_not_found` / `run_not_found` | 对象不存在 |
| 409 | `state_conflict` | revision 或状态不允许 |
| 422 | `case_package_invalid` | 案例包不可执行 |
| 403 | `role_forbidden` | 当前身份无权操作 |

错误响应不得包含本地绝对路径、SQL、堆栈或案例包隐藏答案。

## 25. 前端迁移与动态渲染契约

### 25.1 硬编码清除矩阵

迁移不能只覆盖场景标题和向导步骤。必须逐项清除业务组件中的案例常量：

| 表面 | 必须数据驱动的内容 |
| --- | --- |
| 首页/接诊 | intakeTasks、equipmentOptionGroups、分支规则、上传绑定 |
| 诊断 | diagnosisTasks、阈值、证据、Agent、排除项 |
| 预方案 | 分组、锁定安全项、编辑规则、顺序 |
| 向导 | 步骤、检查项、测量、视觉、完成条件、跳转 |
| 智能体 | 主题、意图、允许步骤、回答和 fallback |
| 检修记录 | 字段、单位、校验、摘要和来源 |
| 作业卡 | 区块、指标、分页、可信度水印 |
| 专家端 | 待审核列表、案例选择、知识选择、审核字段 |
| 图谱 | 案例/知识/版本过滤、增量节点和关系 |
| 管理壳层 | 当前 run、状态、角色可用动作 |

验收标准：除兼容适配层和测试夹具外，业务组件中不得出现 `CASE-ACP4000-001`、`KB-008`、TEMP/FAN、固定风扇温度字段或供电案例 ID。

### 25.2 专家多案例工作台

专家端不复用工程师端的全局 `activeCaseId`。必须维护：

```text
selectedRunId
selectedCaseId
selectedKnowledgeId
selectedVersion
```

待审核列表支持按案例和状态筛选；选中项写入 URL 或等价可恢复页面状态。刷新、后退和打开第二个标签页时不得跳到另一个案例。

### 25.3 智能体主题结构

```json
{
  "id": "power-connector-pins",
  "intents": ["询问接线顺序"],
  "synonyms": ["怎么接", "先接哪个", "这个顺序怎么样"],
  "answerMarkdown": "...",
  "sourceRefs": ["claim-power-connector"],
  "safety": [],
  "allowedStepIds": ["step-power-03-isolate"],
  "applicability": {}
}
```

匹配顺序固定为：

```text
caseId
→ 当前 stepId
→ 当前步骤允许的 topic
→ 宽松意图识别
→ 当前步骤 fallback
→ 通用安全 fallback
```

同一个问题在不允许的步骤不能提前返回操作答案。

### 25.4 视觉内容结构

```json
{
  "visualId": "visual-power-terminal",
  "type": "image",
  "src": "assets/power-terminal.webp",
  "alt": "24V DC 端子接线示意",
  "caption": "断电确认后检查",
  "checkId": "check-power-terminal",
  "manualRef": "claim-power-connector",
  "aspectRatio": "4/3",
  "fallback": "显示文字检查说明"
}
```

图片缺失、加载失败或不支持时必须有文字 fallback。视觉内容不得替代安全文字和测量判据。

## 26. 作业卡、审核、发布和同步

### 26.1 动态作业卡字段

每个工程师字段必须声明：

```text
id / label / type / unit / required / validation / displayOrder / source
```

支持 number、text、select、boolean、datetime 和 attachment-summary。测量值保留原始值及标准化值，PDF 显示单位。生成前服务端验证必填字段、数值范围、步骤完成状态和安全项。

### 26.2 两页约束与快照

- 两页是打印目标和验收门槛；
- 区块支持 `priority`、`keepTogether`、`maxRows` 和溢出摘要；
- 超出容量时先压缩低优先级附件清单，不裁掉安全、结论、处理和恢复验证；
- 合成数据必须显示 `演示构造数据` 水印；
- 生成 PDF 的同时保存 `jobCardSnapshot`、模板版本、渲染器版本和文件哈希；
- 后续案例包或渲染器升级不得改变历史 PDF。

### 26.3 原子发布

发布在一个数据库事务中完成：

1. 锁定并读取当前知识版本；
2. 校验 `expectedCurrentVersion`、run 状态和专家权限；
3. 固化 `expertReviewSnapshot`；
4. 服务端计算下一版本号；
5. INSERT 不可变 `KnowledgeVersion`，禁止 `INSERT OR REPLACE`；
6. INSERT 对应 `GraphVersionDelta`；
7. 更新 run 状态与 revision；
8. 写入审计事件。

任一步失败全部回滚。相同 `idempotencyKey` 不重复创建版本。发布不能把 `synthetic_demo` 升级为 `verified_case`。

### 26.4 工程师同步

- 同步接口显式接收 `knowledgeId + version`；
- 使用可验证 UPSERT，不依赖当前激活案例；
- 同一版本重复同步不生成重复记录；
- 新版本发布后旧版本同步记录保留；
- 知识详情明确显示当前本地版本和可同步版本。

## 27. 分阶段实施与门禁

### 阶段 A：基线冻结

- 备份数据库并记录当前分支、测试和演示截图；
- 建立散热完整链路回归清单；
- 审计散热知识可信等级；
- 输出硬编码清除矩阵。

**门禁：** 当前散热演示可重复运行，已有数据可恢复。

### 阶段 B：基础设施

- 建立 JSON Schema、模块加载器和引用校验；
- 建立数据库迁移器；
- 建立 CaseRun、事件、revision 和幂等机制；
- 建立路由接口和 golden corpus。

**门禁：** 无 UI 参与时，API 可完成加载、路由、建 run、状态流转和冲突测试。

### 阶段 C：迁移散热案例

- 将散热内容迁入模块化案例包；
- 前端接入 CaseSession；
- 全链路改读 stage/role DTO；
- 保持现有效果和步骤问答。

**门禁：** 散热回归通过，业务组件硬编码扫描通过。

### 阶段 D：供电案例

- 完成供电案例包、来源引用和安全审查；
- 接入供电诊断、向导、问答、记录和视觉；
- 完成两页作业卡；
- 完成专家、发布、图谱和同步。

**门禁：** 供电完整演示、刷新恢复、错误状态和安全限制全部通过。

### 阶段 E：扩展性证明

- 增加 `CASE-FIXTURE-003` 最小测试案例；
- 只增加案例数据，不修改业务组件；
- 验证路由、渲染、向导、记录和专家列表均可加载。

**门禁：** 第三案例测试夹具通过，证明架构不是“双案例 if/else”。

### 阶段 F：演示发布

- 执行双案例浏览器验收；
- 执行数据库升级与回滚演练；
- WSL 构建和运行；
- 在目标龙芯环境执行开发态验证；
- 固化演示数据库、案例包哈希、启动脚本和讲解路径。

**门禁：** 交付物可在干净环境复现，演示前重置只创建新 run，不破坏知识资产。

## 28. 测试矩阵与完成定义

### 28.1 自动化测试

| 层级 | 必测内容 |
| --- | --- |
| Schema | 必填、类型、枚举、未知字段、路径逃逸、断裂引用、版本不兼容 |
| 路由 | golden corpus、否定、单位、错字、冲突、阈值、确定性 |
| 状态机 | 合法/非法转换、多 run、并发 revision、重复幂等键 |
| 数据库 | 空库初始化、旧库升级、失败回滚、seed 不覆盖、备份恢复 |
| API | 角色/阶段裁剪、错误码、隐藏答案、缺失 caseId/runId |
| 前端 | 案例切换、请求竞态、刷新恢复、多标签页、专家筛选 |
| 智能体 | case→step→intent、同义问法、越步骤拒答、安全 fallback |
| PDF | 两页、分页溢出、单位、来源、水印、快照重现 |
| 发布 | 原子性、版本冲突、可信度不升级、图谱版本过滤 |
| 扩展性 | 第三 fixture 案例零业务组件改动加载 |

### 28.2 浏览器重点场景

除第 13 节主路径外，增加：

1. 同时打开散热和供电两个运行，验证互不串状态；
2. 案例切换时旧诊断请求晚返回，页面仍保持新案例；
3. 上传材料后切换候选，系统要求确认是否复用；
4. 专家在两个标签页审核不同 run，不相互覆盖；
5. 同一发布请求重复提交，只产生一个知识版本；
6. PDF 内容超长时仍保留安全项、结论、处理和恢复；
7. 查询“本次新增与修改”只出现所选知识版本的图谱增量；
8. 未支持故障不会跳入散热或供电向导。

### 28.3 Definition of Done

本功能只有同时满足以下条件才算完成：

- 两个正式案例都能从首页输入走完整链路；
- 所有正式案例包和引用通过 Schema 校验；
- 案例模板和运行实例完全分离；
- SQLite 可从现有演示库无损迁移；
- 关键写操作具备 revision、幂等和事务保护；
- 页面不存在影响扩展性的案例硬编码；
- 专家审核、知识发布、图谱和同步均按 run/knowledge/version 隔离；
- 作业卡在规定数据下稳定输出两页；
- 第三 fixture 案例无需改业务组件即可运行；
- 自动化测试和浏览器验收有可保存的结果；
- 合成数据、官方事实和真实案例证据在页面及 PDF 中不混淆。

## 29. 开发前必须冻结的实现参数

以下不是产品方向问题，但必须在阶段 B 编码前以配置或 ADR 形式冻结：

1. 路由 `minScore`、`minMargin`、同分规则和算法版本；
2. CaseRun ID、知识版本号和幂等键格式；
3. 支持的 JSON Schema 版本范围；
4. CaseRun 各状态允许的角色和转换；
5. SQLite 迁移版本、备份位置和失败恢复方式；
6. 作业卡两页的纸张、边距、字体、最大行数和溢出策略；
7. 官方手册引用的页码口径和证据审阅人；
8. 散热案例当前可信等级的审计结论；
9. 演示数据库重置边界和演示账号权限；
10. 目标 WSL、浏览器和龙芯开发环境的版本基线。

这些参数确定后才能进入基础设施开发。参数调整应更新配置、测试语料或 ADR，不应散落在组件条件判断中。
