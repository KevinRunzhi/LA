## 2. 项目与比赛文档目标

项目正式名称为“工控设备智能检修与知识作业系统”。比赛要求提交：

1. 软件功能需求分析文档；
2. 软件功能设计文档；
3. 软件产品说明书；
4. 软件功能测试报告；
5. 软件安装包及部署文档。

文档面向比赛评审和产品交付，应使用完整、正式的产品表述，重点说明系统解决的问题、已经形成的能力、功能间的业务闭环及实际使用方法。开发阶段的临时实现方式不应直接成为正式文档的产品定位。

系统核心业务主线：

`工业现场异常接入 → 设备与故障识别 → 检修资料与知识检索 → 智能辅助诊断 → 步骤化检修 → 专家审核 → 检修记录与作业卡输出 → 案例、知识和图谱回流`

正式材料应以“工控机”或“工控设备”为中心，不把产品范围限定为研华 ACP-4000、IPC-610 或其他某个具体型号。具体型号可以作为案例、手册或设备记录出现。

## 3. 写作边界与统一口径

### 3.1 文档边界

- 《软件功能需求分析文档》回答为什么建设、面向谁、需要什么能力和有哪些约束，不展开具体实现。
- 《软件功能设计文档》回答如何实现，包含架构、模块、数据、接口、安全和部署设计。
- 《软件产品说明书》面向使用者与评审人员，说明产品用途、功能入口、业务操作、输出结果和注意事项。
- 《软件功能测试报告》说明测试依据、范围、环境、方法、用例、执行结果、缺陷和结论。未实际执行的用例不能直接写成“通过”。
- 《软件安装包及部署文档》说明安装包、环境、部署、配置、运行、验证、备份和故障排查。

### 3.2 已确定规则

- 需求分析不使用 `FR-xxx` 功能编号，通过稳定的章节标题建立对应关系。
- 需求分析已经删除“功能优先级”。
- 软件功能设计文档已经删除“修订记录”。
- 正式产品文档避免“演示、模拟、占位、写死、尚未实现、以后接入、临时数据”等开发口吻。
- 需求、设计和产品说明可按目标交付形态描述；测试报告的执行记录、通过结论和证据必须来自真实测试。
- “散热异常”是唯一需要完整、细致展开的业务闭环案例。其他领域通过知识库、手册、案例和知识图谱体现覆盖广度，不必扩写为同等深度的闭环。

## 7. 已确定的产品功能

### 7.1 工程师端

- 工程师工作台和任务入口；
- 异常接入，支持文本、语音、图片、视频和音频；
- 首页“检修资料”选择器，可从案例、手册和知识中选择，状态持续至异常接入完成；
- 设备与故障识别确认；
- 智能诊断与多角色协同分析呈现；
- 可调整的检修前方案；
- 步骤化检修向导和当前步骤问答；
- 语音播报和专家视频协同；
- 恢复运行验证；
- 不同型号、不同故障的检修记录；
- 两页 A4 总结式检修作业卡 PDF；
- 与专家端统一视觉风格的只读知识图谱页面。

标准检修步骤：

1. 确认告警与定位设备；
2. 执行安全准备；
3. 检查机柜环境与风道；
4. 检查滤网、风扇和接线；
5. 恢复运行与验证。

步骤 4 规划了重点追问：“这个接线顺序是怎么样的？”和“风扇转速偏低可能是什么情况导致的？”。细化回答只应在“检查滤网、风扇和接线”的上下文中出现。

### 7.2 专家端

包括专家工作台、全部案例、检修知识库、检修手册、知识图谱、专家审核、知识回流和设置。

审核流程：

1. 审核并修正案例；
2. 修正知识与知识图谱；
3. 确认并发布。

工程师现场证据只读保留，专家可修正诊断结论、知识和图谱关系。审核决定包括“修正后通过”“退回补充”“仅归档案例”，发布后应可验证知识检索结果。

### 7.3 后台管理

后台管理作为独立入口，包含用户统计、查询筛选、新增和编辑工程师或专家、组织字段、启用停用、密码重置以及管理审计边界。

### 7.4 知识图谱

仅含两个核心视图：

1. 全局知识图谱；
2. 本次新增与修改。

交互包括节点点击、缩放、平移、搜索、聚焦和详情。专家审核时可修改知识和关系，工程师只读查看已发布版本。图谱以工控机为中心覆盖多类故障，点击局部节点后放大相关信息。

### 7.5 作业卡

作业卡定位为可打印、可归档的两页 A4 PDF，包含任务与设备概况、故障现象、诊断结论、关键检修摘要、处理结果、恢复验证、人员时间、审核信息、依据和签字区域。不要把向导里的全部交互和冗长操作步骤堆入 PDF。
