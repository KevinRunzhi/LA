# 参加挑战赛理由及作品亮点

## 一、作品基本情况

| 项目 | 内容 |
| --- | --- |
| 作品名称 | 工控设备智能检修与知识作业系统 |
| 作品方向 | 基于多模态大模型的设备检修知识检索与标准化作业 |
| 主要用户 | 一线检修工程师、检修专家、用户管理员 |
| 主要对象 | 工控机及其供电、散热、存储、主板、通信和监控部件 |
| 目标环境 | LoongArch 架构、银河麒麟操作系统 |

## 二、我们为什么还想参加挑战赛

正赛没有通过以后，我们认真回看了自己的作品，也重新看了当时准备的介绍材料。我们的感受是，项目并不是没有内容，而是内容铺得太多，介绍时又希望把每一个页面都讲到，最后反而没有把最重要的一条线讲清楚。评委可能看到了异常接入、智能诊断、检修向导、知识库和知识图谱等许多功能，却不容易在有限时间内理解这些功能为什么要放在一起，以及它们怎样共同完成一次设备检修。

经过这段时间的整理，我们认为这件作品真正值得继续做下去的地方，不是页面数量，也不是接入了多少种模型，而是我们已经把“现场检修”和“知识积累”连在了一起。

工程师在现场处理一次异常时，会产生设备信息、故障现象、图片、声音、运行参数、检查结果和实际处理措施；专家审核时会进一步修正诊断结论和知识关系。过去这些内容往往分散在纸质记录、聊天记录、个人笔记和不同厂商的设备手册中，一次检修完成以后，很难直接变成下一次检修能够使用的知识。我们希望通过这套系统，把一次检修留下的有效经验整理成案例、知识条目和图谱关系，让后来的工程师能够找到、看懂并在合适的设备和步骤中使用。

因此，我们申请参加挑战赛，主要有以下几个理由。

### 1. 项目面对的是一个具体而长期存在的问题

工业现场的工控设备品牌和型号较多，同一种表面现象可能对应完全不同的故障原因。例如设备温度升高，既可能是风扇停转、滤网堵塞或风道受阻，也可能与环境温度、监控阈值、风扇接线和供电状态有关。工程师不能只凭一句“大概率是散热问题”就开始拆机，还需要核对设备手册、告警状态、风扇转速、系统温度和现场环境。

现实工作中，资料通常散落在不同目录和不同格式的文件中。经验丰富的人员知道应该先看什么，新员工则可能需要花很长时间查找，也容易把同系列设备的接线位置、备件型号或参数阈值直接套用到当前设备。我们所做的系统，正是希望把现场信息、设备资料、历史案例和检修步骤放到同一个任务里，帮助工程师更快地找到依据，同时保留人工确认和安全边界。

### 2. 项目已经有一条可以实际走通的业务主线

作品目前围绕一次完整检修任务组织功能，而不是把多个独立页面拼在一起。主线已经明确为：

> 现场异常接入 → 设备与故障识别 → 检修资料检索 → 智能辅助诊断 → 检修方案确认 → 步骤化检修 → 恢复运行验证 → 专家审核 → 检修记录与作业卡输出 → 案例、知识和图谱回流。

我们希望挑战赛评委看到的是一项从开始到结束都能够说明白的检修任务，而不是单独评价某个按钮或某个问答窗口。

### 3. 项目已经积累了一批可以继续使用的设备资料

在开发过程中，我们逐步整理了不同品牌和型号的工控设备手册，包括机架式、箱式和面板式工控机的用户手册、安装说明和故障排查资料。知识内容不仅包括散热，还涉及环境工况、外部供电、电源模块、存储设备、主板与底板、显示、通信接口、监控告警、RTC 电池以及安装检修不规范等问题。

这些资料并不是只作为文件列表展示。我们正在按照设备、部件、故障现象、可能原因、检查方法、处理措施、安全风险和资料来源进行整理，使它们能够进入检修知识库、参与检索，并在知识图谱中建立关系。

目前散热异常的知识链最完整，已经能够从告警和现场现象一直追溯到检查、处理和恢复验证。其他故障领域已经具备手册和知识基础，下一步会按照相同结构逐步补充案例和关系。我们没有把产品限定为某一台具体型号，而是希望先把知识组织方法和检修流程建立起来，再逐步扩展新的设备。

### 4. 项目已经从“给答案”走到了“辅助作业”

我们一开始也做过比较普通的智能问答，但后来发现，工程师在检修现场真正需要的并不只是一个答案。他更关心当前设备是什么、现在做到哪一步、接下来应该核对什么、哪些操作有风险，以及回答依据的是哪一份手册。

所以，我们把检修智能体放入检修向导，让它能够结合当前设备、当前任务、当前步骤、已选择资料和已经记录的现场结果回答问题。工程师执行到“检查滤网、风扇和接线”时，可以继续询问风扇接线顺序，也可以询问风扇转速偏低可能由哪些情况导致。回答的范围由当前步骤约束，不会突然跳到无关故障，也不会把型号专用信息当作通用结论。

这种做法比单独放一个聊天窗口更麻烦，但更接近现场使用方式，也是我们认为作品值得继续打磨的地方。

### 5. 项目具有明确的国产化应用方向

作品面向 LoongArch 架构和银河麒麟操作系统规划运行和部署方式。我们不仅考虑前端页面和大模型调用，也同步考虑业务服务、数据库、文件资源、向量检索、知识图谱、离线依赖、启动停止和运行验证等问题。

目前项目已经建立需求分析、功能设计、产品说明、功能测试和安装部署文档体系。挑战赛阶段，我们希望在真实目标环境中继续核对软件依赖和核心业务流程，把“能够运行”进一步落实为有安装步骤、有验证记录、有问题说明的交付结果。

### 6. 正赛复盘后，我们知道下一步应该把精力放在哪里

正赛未通过让我们意识到，继续增加页面并不能自然地提高作品质量。后续最需要做的是把核心流程做稳，把诊断依据讲清楚，把知识更新机制做完整，并且用真实测试和目标环境运行结果证明作品。

我们已经停止继续横向铺开不必要的功能，接下来会围绕完整检修案例、检索与问答质量、专家审核、知识图谱更新、作业卡输出和国产化环境验证集中完善。挑战赛给我们的价值，不只是再参加一次比赛，而是让团队有一个明确节点，把已经投入大量时间的项目认真收尾并形成可以交付的成果。

## 三、如果评委现场查看，我们希望这样介绍作品

为了让作品的主线更容易理解，可以从一项工控机散热异常任务开始查看。

### 第一步：接入现场异常

值班人员发现站控机柜内工控机温度告警，同时伴有风扇声音异常。工程师进入系统后，可以用文字或语音描述现象，补充发生时间和设备位置，并接入现场图片、视频、音频以及 TEMP/FAN 告警、风扇转速、系统温度和 CPU 温度等运行信息。

在任务开始时，工程师还可以从检修知识库中选择与当前设备和故障有关的历史案例、知识条目或设备手册。选择结果会保留在当前任务中，而不是选择后立即消失。

### 第二步：确认设备和故障方向

系统根据异常描述、设备信息和现场材料形成设备识别及故障方向。工程师需要核对识别结果，确认当前设备、告警和初步故障领域。如果现场信息不足，系统会提示补充，而不是直接给出确定结论。

这一步的作用是先把事实确认清楚。后面的检索和检修建议都围绕经过确认的信息展开，减少从错误型号或错误现象出发继续推理的情况。

### 第三步：查看诊断依据并确认检修方案

系统结合历史案例、知识条目、设备手册和知识图谱关系，给出可能原因、判断理由、风险提示和建议检查方向。工程师可以看到系统参考了哪些资料，也可以调整检修预方案。

检修预方案不是模型输出后立即执行的指令。工程师可以根据现场条件增加、删除或调整普通步骤；断电、挂牌、冷却、防静电等关键安全要求应当保留。只有工程师确认方案后，任务才进入检修向导。

### 第四步：按照向导逐项检查

当前完整案例采用五个步骤：

1. 确认告警与定位设备；
2. 执行安全准备；
3. 检查机柜环境与风道；
4. 检查滤网、风扇和接线；
5. 恢复运行与验证。

每一步都包含检查目标、现场资料、操作提醒和结果记录。工程师可以按需要查看设备图片和手册摘录，也可以使用当前步骤智能体继续追问。

检修向导将阶段进度、当前检查项、设备资料和检修智能体放在同一个工作界面中。工程师不需要离开当前任务另行查找聊天入口，也不需要在提问时重新解释设备和故障背景。智能体沿用本任务已经确认的信息，回答内容只围绕当前步骤展开。

工程师可以通过文字追问，也可以使用语音输入和语音播报。语音识别结果先回填为可编辑文字，经工程师核对后再进入任务记录；语音播报则用于朗读当前步骤建议和注意事项，减少现场戴手套或不方便持续操作键盘时的交互负担。

### 第五步：在需要时查看具体设备资料

检修步骤使用的结构、接口和接线信息来自已经整理的设备资料，并与当前检查内容对应。例如检查风扇时，工程师可以先确认风扇模块的安装位置，再核对监控板上的 FAN1、FAN2 等接口标识，并结合设备手册确认风扇数量、供电方式和监控信号。

对于型号相关的接线位置、拆装方式和参数，系统应提示工程师核对目标设备手册。相似型号资料可以帮助理解故障方向，但不能替代当前型号的正式依据。

当前步骤追问也遵守这一原则。当工程师询问“接线顺序是怎样的”时，系统首先说明需要核对目标设备的接口标识和手册，而不是把某一型号的 FAN1、FAN2 位置直接作为所有设备的通用接线方法。当工程师询问“风扇转速偏低可能是什么情况导致的”时，回答会分别提示滤网或风道阻力、风扇积尘和磨损、供电异常、接插件接触不良、调速策略以及转速采集故障等方向，并要求结合现场数据逐项排查。

### 第六步：完成恢复运行验证

处理完成后，工程师需要记录设备复装情况、告警状态、风扇转速、系统温度、CPU 温度和观察结果。系统不会因为某个步骤点击完成就自动判定设备恢复，而是要求对关键指标进行确认。

恢复验证一方面帮助工程师判断本次处理是否有效，另一方面也为专家审核和后续案例复用保留结果依据。

### 第七步：专家审核检修结果和知识变化

工程师提交任务后，专家可以查看现场原始事实、诊断依据、实际措施和恢复结果。原始证据保持可追溯，专家主要修正故障结论、知识内容和图谱关系。

专家审核分为三个环节：审核并修正案例、修正知识与知识图谱、确认并发布。根据资料完整程度和结论质量，可以选择“修正后通过”“退回补充”或“仅归档案例”。未经审核的经验不会直接进入正式知识库。

### 第八步：形成记录、作业卡和新知识

系统将整项任务整理为结构化检修记录，并生成适合两页 A4 打印的 PDF 作业卡。作业卡保留设备信息、故障现象、诊断结论、关键处理、恢复结果、风险和审核信息，不把页面中的所有交互原样堆入文档。

审核通过后，本次任务可以形成新的历史案例、知识条目或图谱关系。知识图谱通过“全局知识图谱”和“本次新增与修改”两个视图，分别展示已有知识结构和本次审核带来的变化。至此，一次现场检修才真正完成闭环。

### 本次任务中的信息怎样继续流转

一次检修任务中的信息不是在页面切换时重新生成，而是按照业务阶段逐步补充和确认。

| 业务阶段 | 主要信息 | 形成的结果 | 后续用途 |
| --- | --- | --- | --- |
| 异常接入 | 异常描述、语音转写、图片、视频、音频、设备位置和运行参数 | 异常事件和现场材料集合 | 用于设备识别、资料筛选和初步诊断 |
| 设备与故障确认 | 设备类型、品牌型号、告警状态和故障领域 | 经工程师确认的任务对象 | 限定知识检索范围，减少错误型号资料混入 |
| 知识检索与诊断 | 手册、案例、知识条目、图谱关系和现场事实 | 故障方向、判断依据、风险和信息缺口 | 用于形成检修预方案 |
| 方案与检修 | 检修阶段、检查项、安全要求和现场结果 | 实际执行过程和处理措施 | 用于恢复验证和检修记录 |
| 恢复验证 | 告警、转速、温度、复装和观察结果 | 是否恢复运行的判断依据 | 用于工程师提交和专家审核 |
| 专家审核 | 原始事实、诊断结论、处理结果和拟更新知识 | 审核结论、修正意见和发布决定 | 决定案例和知识是否进入正式版本 |
| 知识回流 | 审核通过的案例、知识条目和图谱关系 | 新的知识版本 | 用于后续相似任务的检索和诊断 |

这种数据流转方式有两个作用：一是避免后续环节脱离现场事实重新生成内容；二是保留每一项结论从哪里产生、经过谁确认以及最终如何进入知识体系的过程。

## 四、作品最重要的几个亮点

### 1. 围绕任务组织智能能力，而不是围绕模型组织页面

作品的核心对象是检修任务。语音识别、图片接入、知识检索、智能问答和知识图谱都服务于同一任务，不要求用户在多个彼此无关的工具之间来回切换。

这种组织方式看起来没有单独展示模型能力那么直接，但它更符合实际工作：现场人员关心的是能否把设备修好并留下完整记录，而不是分别体验文字模型、视觉模型或语音模型。

### 2. 诊断建议尽量说明依据和适用范围

设备检修不能只给出“可能是风扇故障”这样的笼统结论。系统需要同时说明判断来自哪些现场事实、关联了哪些手册或案例、还缺少什么信息，以及哪些内容只适用于特定型号。

我们将“知识有来源、建议可复核”作为设计原则。工程师可以查看参考资料，专家也可以在审核时检查诊断与资料是否匹配。这样做不能完全消除模型出错，但能够让错误更容易被发现和纠正。

### 3. 当前步骤问答比通用问答更贴近检修现场

同一个问题在不同步骤中可能需要完全不同的回答。例如“现在可以拆吗”必须结合是否断电、是否完成挂牌和设备温度判断；“转速为什么低”则需要结合滤网、风道、接线、供电、风扇磨损和监控采集状态分析。

系统把当前步骤、目标设备、已选资料和现场记录一起作为问答上下文，使回答尽量贴近工程师眼前正在做的事情。语音输入和播报则进一步降低了现场交互负担。

### 4. 工程师确认和专家审核共同控制风险

我们没有把大模型设定为最终决策者。设备识别需要工程师确认，检修方案允许工程师修改，关键安全步骤受到保护，恢复运行需要记录实际指标，知识更新还要经过专家审核。

这个设计来自工业检修的实际要求：智能系统可以帮助查找资料和整理判断，但不能绕开现场责任人，也不能让一次未经核对的回答直接成为组织知识。

系统中的责任边界也比较明确：模型负责资料匹配、内容归纳和辅助建议；工程师负责确认现场事实、检修方案和实际操作；专家负责审核故障结论和知识更新；管理员负责账号、角色和组织信息。涉及设备停机、拆装、送电和恢复运行的决定，仍由具备相应职责的现场人员作出。

### 5. 检修知识库和知识图谱各自解决不同问题

知识库适合阅读手册、案例和具体处理内容，知识图谱适合查看设备、部件、故障、原因和措施之间的联系。如果只做知识库，资料之间的关联不直观；如果只做图谱，工程师又很难看到完整原文和操作依据。

因此，系统同时保留两种组织方式，并让专家在审核过程中维护知识内容和图谱关系。本次新增与修改视图还能帮助专家判断一次检修到底改变了哪些知识。

### 6. 检修结束后能够留下可直接使用的成果

许多智能系统的输出停留在聊天记录。本作品在任务结束后形成检修记录和 PDF 作业卡，便于班组交接、设备档案、复盘和责任追溯。经过审核的经验还可以继续进入知识库和知识图谱。

这意味着系统的最终成果不只是“一段回答”，而是一份可以归档的检修记录和一批经过确认的知识更新。

### 7. 知识结构可以继续扩展到其他设备和故障领域

当前以工控机为主要对象，是为了先把设备、部件、故障、原因、措施和依据之间的关系建立清楚。现有资料已经覆盖多个品牌和多种设备形态，也包含散热以外的启动、供电、存储、显示、通信和监控问题。

后续新增设备时，不需要重新设计一套完全不同的系统，只需补充设备目录、手册、案例、知识条目和关系，并对专用参数及操作方法进行核验。这使项目具备继续扩展的基础。

## 六、目前已经形成的成果

### 1. 工程师端

工程师端已经围绕现场检修形成较完整的操作路径，包括异常接入、检修资料选择、设备与故障确认、辅助诊断、检修预方案、步骤化向导、当前步骤追问、语音输入与播报、专家协同、恢复验证、检修记录和 PDF 作业卡。

检修记录中可以展示不同型号和不同故障领域的任务，使系统不只围绕单一案例组织数据。工程师端还提供知识图谱查看能力，便于在检修过程中了解设备、部件、故障原因和处理措施之间的关系。

### 2. 专家端

专家端包括专家工作台、全部案例、检修知识库、设备手册、知识图谱和审核发布流程。专家可以查看工程师提交的现场证据，修正诊断结论和知识内容，并决定通过、退回或仅归档。

知识图谱界面保留全局视图和本次新增修改视图。专家可以点击、缩放、搜索和聚焦节点，并在审核过程中检查或调整知识关系。

### 3. 管理端

管理端用于维护工程师和专家账号、角色、组织归属及启停状态，并提供查询、筛选、新增、编辑和密码重置等功能。虽然用户管理不是作品最主要的创新点，但它是软件从单人使用走向多角色协作所需要的基础能力。

### 4. 检修知识与资料

项目已经整理多份 Rockwell、Schneider Electric 和其他工控设备资料，内容包括用户手册、安装说明、故障排查指南和散热相关资料。知识范围覆盖环境、供电、硬件部件、配置维护、通信和监控告警等类别。

资料整理工作仍会继续，但现有内容已经能够支持典型散热异常闭环，并为其他故障领域的扩展提供来源。

### 5. 软件文档和交付材料

项目已经形成软件功能需求分析、软件功能设计、软件产品说明、软件功能测试和安装部署等文档。我们希望最终提交的不只是源代码和展示视频，还包括能够说明功能边界、设计方法、测试结果和安装方式的完整材料。

### 6. 评委可以直接核验的内容

作品不需要依靠团队口头解释才能证明主要功能。评委可以按照一项检修任务依次核验以下内容：

1. 异常描述、设备信息、运行参数和现场材料能否进入同一任务；
2. 检修资料选择后，状态能否保留并继续用于后续环节；
3. 辅助诊断能否说明故障方向、判断理由和参考资料；
4. 检修预方案能否由工程师修改和确认，关键安全要求是否得到保留；
5. 检修智能体的回答是否与当前设备和当前步骤相关；
6. 工程师能否记录每一步的检查和处理结果；
7. 恢复运行验证是否要求填写告警、温度、转速和观察结果；
8. 专家能否查看原始事实、修正结论并处理知识更新；
9. “本次新增与修改”图谱是否能够反映本次任务带来的知识变化；
10. 系统能否形成检修记录和适合打印归档的 PDF 作业卡。

这一核验顺序与展示视频的业务顺序保持一致。即使评委只选择其中几个环节查看，也能够看到上一步信息如何进入下一步，而不是只能看到孤立的页面效果。

## 七、为什么我们认为作品值得获得一次挑战赛机会

我们理解，挑战赛名额有限，评委需要判断一项作品是否值得继续投入评审资源。我们不希望用“已经投入很多时间”作为主要理由，因为投入本身不能证明作品价值。我们认为作品值得继续评审，主要基于以下几点。

第一，作品面对的需求真实且具体。工业现场确实存在资料分散、检修依赖经验、过程难以统一和知识难以沉淀的问题。

第二，作品已经形成一条完整主线。工程师端、专家端、知识库、知识图谱和作业卡之间存在实际数据和业务关系，不是彼此独立的展示页面。

第三，作品与普通大模型问答有明确区别。智能能力受到任务上下文、当前步骤、资料来源、工程师确认和专家审核的共同约束。

第四，现有成果可以通过一项完整检修任务现场核验。评委能够看到信息怎样进入系统、建议依据什么产生、工程师怎样执行、专家怎样审核，以及最后留下什么结果。

第五，作品兼顾智能化和国产化方向。我们希望在 LoongArch 和银河麒麟环境中验证完整业务流程，而不是只在常规开发环境中完成页面。

第六，项目有继续扩展的资料和结构基础。当前以散热异常为完整案例，但知识库和图谱已经按多设备、多部件和多故障领域组织，不需要把整个系统限定在单一案例中。

正赛没有通过说明我们的作品和表达仍有不足。我们接受这个结果，也通过复盘找到了问题。申请挑战赛不是希望回避原有不足，而是希望用后续完成度、真实验证结果和更清楚的作品主线证明这项工作值得继续。

本团队申请参加挑战赛，希望继续完善“工控设备智能检修与知识作业系统”。正赛结束后，我们重新复盘了作品，发现之前的介绍过于强调页面和功能数量，没有把最重要的业务主线说明清楚。作品真正想解决的，是工业现场设备资料分散、故障判断依赖个人经验、检修步骤难以统一，以及一次检修结束后经验难以继续复用的问题。

作品还建立了专家审核和知识回流机制。专家可以核对现场证据、修正诊断结论和知识图谱关系，审核通过的经验进入历史案例、检修知识库和知识图谱，继续服务后续任务。这样，一次检修不仅解决当前故障，也能够为组织留下经过确认的知识。

作品以工控机为主要对象，现有资料覆盖不同品牌和型号，并涉及环境、供电、散热、存储、主板、通信、监控和运维不当等多类故障。系统面向 LoongArch 架构和银河麒麟操作系统规划运行与部署。我们希望通过挑战赛完成国产化环境验证、检索与问答质量校准、多故障案例补充、功能测试和安装交付完善，让评委通过一项完整、可核验的检修任务重新评价作品的实际价值。
