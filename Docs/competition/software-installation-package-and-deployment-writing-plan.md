# 工控设备智能检修与知识作业系统

# 软件安装包及部署文档详细编写计划

> 执行状态：Spec 及第1—9批内容已全部完成；正式文档进入最终安装包参数冻结和目标机实测回填阶段。

## 1. 计划目标

依据《软件安装包及部署文档大纲》，分批完成面向最终参赛交付版本的正式《软件安装包及部署文档》。文档以 LoongArch64、银河麒麟 V10 系列目标环境和目标技术架构完整随包部署为主线，最终使部署人员能够仅依靠安装介质和本文档完成：

> 交付物核对 → 环境检查 → 离线安装 → 安全配置 → 数据初始化 → 服务启动 → 部署验收 → 运行维护 → 备份恢复 → 升级回退 → 安全卸载。

## 2. 总体编写原则

1. **目标架构优先。** 正文以 Vue 3、Nginx、FastAPI/Uvicorn、Celery、PostgreSQL/pgvector、Redis、Neo4j、文件资源库、Prometheus/Grafana 和 systemd 的最终交付形态为准。
2. **完整随包交付。** 系统组件、运行环境、离线依赖、配置模板、初始化数据和维护脚本均按照离线安装介质随包提供的方式描述，不把临时联网下载作为标准步骤。
3. **模型边界清晰。** 统一模型网关、客户端、配置模板和检查工具随包部署；千问语言、OCR、ASR、向量化和重排序服务根据最终网络与算力方案接入，不把外部 API 写成本机安装组件。
4. **事实与待验证项分开。** 已确定的技术职责和部署关系直接写入正文；组件固定版本、硬件容量和 LoongArch64 兼容性等未冻结内容使用集中参数表管理，不在不同章节随意猜测。
5. **两种 Neo4j 拓扑并行保留。** 同时编写 LoongArch64 原生部署和独立兼容节点部署路径，最终依据专项验证结果确定推荐方案。
6. **命令可执行。** 正式正文中的目录、端口、服务名、账号、脚本和命令必须前后一致；未形成脚本前先定义命令接口，不伪造执行结果。
7. **操作可恢复。** 覆盖、删除、迁移、恢复和卸载前必须确认目标并建立备份或回退点。
8. **跨文档一致。** 产品名称、角色、功能范围、目标平台、技术组件、核心流程和测试边界与其他四份比赛文档保持一致。

## 3. 编写前统一准备

在正式分批编写前先建立一份“部署参数冻结表”，贯穿全文维护，至少包含：

| 参数组 | 需要确定的内容 | 当前处理方式 |
| --- | --- | --- |
| 产品与安装包 | 产品版本、构建号、包名、SHA-256、目标架构 | 先定义字段，最终打包后回填 |
| 节点 | 业务节点、Neo4j节点、模型节点数量及地址 | 先支持单节点与多节点两种拓扑 |
| 组件版本 | Python、Nginx、FastAPI、PostgreSQL、pgvector、Redis、Neo4j、Prometheus、Grafana等 | 建立集中表，待兼容性验证后冻结 |
| 服务名称 | systemd单元、运行账号、启动依赖 | 在第4—6批统一确定 |
| 目录 | 程序、配置、数据、文件、日志、临时目录、备份目录 | 第2批形成统一目录表 |
| 端口 | Nginx、Uvicorn、PostgreSQL、Redis、Neo4j、Prometheus、Grafana、模型网关 | 第2批形成统一端口表 |
| 安全参数 | TLS、JWT、会话、数据库账号、模型密钥、文件权限 | 第4批集中设计 |
| 容量 | CPU、内存、磁盘、并发、数据规模 | 先写测量方法，目标机验证后回填 |
| 备份 | 周期、保留、RPO、RTO、备份介质 | 第7批形成建议值和待确认项 |
| 验收 | 健康、组件、业务闭环、监控、恢复 | 第6批与测试报告统一 |
