# 工控设备智能检修与知识作业系统阶段总结

## 1. 总结说明

本文记录项目从最初的单案例界面原型发展到比赛提交平台后的最终阶段状态，作为项目暂停或结束后的长期交接材料。以后如果重新启动开发，应先阅读本文，再阅读 `Docs/README.md`、比赛提交架构、部署指南和功能矩阵。

项目结束时的最新代码基线为 `submission/competition-platform`。该分支在早期演示流程基础上，进一步完成了模块化案例包、服务端案例路由、CaseRun 状态机、核心业务服务、平台运维、案例审核发布和资料驱动的多 Agent 案例生成。最终归档后，GitHub `main` 应与该基线保持一致。

需要特别说明：仓库中同时保存了“当前真实实现”和“比赛文档中的目标产品架构”。当前真实实现采用 React、Vite、Flask、Gunicorn、SQLite 和本地文件存储；比赛目标架构文档中出现的 Vue、FastAPI、PostgreSQL、pgvector 和 Neo4j 是产品化设计方案，不应当被误认为当前源码已经全部采用这些技术。

## 2. 项目最初要解决的问题

项目面向油气场站、制造和能源等工业环境中的工控设备检修。实际工作中主要存在以下问题：

1. 设备品牌、型号和硬件版本较多，故障现象相似但处理方法可能不同；
2. 厂商手册、检修规程、历史案例和专家经验分散保存；
3. 一线人员在故障发生后需要人工翻阅大量资料，检索效率较低；
4. 检修过程依赖个人经验，安全要求、检查顺序和结果记录不统一；
5. 一次检修完成后，现场事实和处理经验难以形成可继续复用的组织知识；
6. 新员工缺少将设备结构、故障原因和标准作业联系起来的学习工具；
7. 工业软件还需要考虑国产处理器、银河麒麟和离线环境中的部署与维护。

项目围绕这些问题逐步形成统一业务闭环：

> 异常接入 → 设备与故障确认 → 资料与知识检索 → 辅助诊断 → 检修方案确认 → 步骤化检修 → 恢复验证 → 专家审核 → 记录与作业卡输出 → 案例、知识和图谱回流。

## 3. 项目推进过程

### 3.1 第一阶段：建立可运行的单案例 MVP

项目最早以工控机散热异常为主案例，完成登录、异常接入、诊断结论、五步检修向导、恢复验证、检修记录、专家审核和知识图谱基础页面。该阶段的主要目标是先把业务主线跑通，并确定工程师和专家两类角色的工作边界。

散热异常案例形成了目前内容最完整的知识链，包括温度告警、风扇转速、滤网和风道、风扇接线、清理和更换、恢复参数以及专家审核。它仍然是理解整套系统最直接的案例。

### 3.2 第二阶段：重构现场异常接入和检修方案

旧版固定翻页接入方式逐步改造成动态接诊工作区。现场描述、位置、设备、告警和运行参数按状态逐步生成，并由工程师确认。图片、视频、音频和检修资料进入同一任务，已选资料持续关联到后续诊断和摘要。

诊断完成后不再直接进入固定向导，而是先形成可编辑检修预方案。工程师可以调整普通步骤，断电、挂牌、冷却、防静电等关键安全项受到保护。确认后的方案被固化并驱动后续检修记录。

### 3.3 第三阶段：补齐工程师、专家和管理员协作

工程师端增加当前步骤问答、语音输入、语音播报、专家协同、恢复验证、不同型号检修记录和两页 A4 PDF 作业卡。检修智能体不再作为脱离任务的通用聊天窗口，而是结合当前设备、当前步骤、已选资料和现场记录回答问题。

专家端形成三步审核：审核并修正案例、修正知识与知识图谱、确认并发布。工程师提交的原始事实保持可追溯，专家修正结论、知识和关系。知识图谱保留“全局知识图谱”和“本次新增与修改”两个视图。

管理员端补充用户统计、查询筛选、工程师和专家账号维护、组织信息、启停状态及密码重置，为多角色使用提供基础。

### 3.4 第四阶段：扩充检修知识和多故障内容

项目整理了多品牌工控设备资料，不再只围绕散热、风扇和滤网。资料内容覆盖环境工况、供电、电源模块、存储、主板与底板、通信接口、显示、RTC 电池、监控告警、粉尘、凝露及不规范运维等领域。

在散热案例之外，进一步建立 Rockwell 6300 供电故障案例，并把案例拆分为 intake、diagnosis、guide、assistant、output、feedback-and-graph 等模块。这样不同案例可以拥有不同的接入字段、诊断规则、检修步骤、问答范围和输出内容。

### 3.5 第五阶段：建立可审计的案例运行平台

为了摆脱前端硬编码案例，后端增加模块化 CasePackage、严格 JSON Schema、路径与引用校验、内容哈希和服务端案例路由。每一次检修创建 CaseRun，并保存 revision、事件日志、检修方案快照、步骤执行、工程师提交和专家审核快照。

写操作具有状态、角色、revision 和幂等校验。知识发布与 CaseRun、案例版本和 package hash 绑定；图谱增量与知识版本绑定。没有现场证据时，系统拒绝把内容升级为 `verified_case`。

### 3.6 第六阶段：补齐核心业务和生产部署能力

比赛提交分支增加了用户会话、密码哈希、令牌撤销、角色权限和审计记录；增加 PDF 手册入库、按页提取、分块、FTS 检索和证据引用；增加图谱变更草稿、审核、发布、全量版本和版本差异；增加检修工单和服务端 PDF 作业卡。

运行层增加 Gunicorn、systemd、可选 Nginx、统一配置、存活和就绪检查、请求 ID、Prometheus 指标、数据库迁移、preflight、SQLite 备份恢复、完整性检查和 GitHub Actions。默认部署仍为单机方式，兼容当前演示链路时使用单 worker 多线程。

### 3.7 第七阶段：形成案例生产、审核和发布中心

案例包从“开发人员直接编辑 JSON”进一步升级为草稿、校验、审核、发布和回滚流程。专家可以克隆已有案例，编辑 registry、manifest 和六个业务模块，运行与生产加载器一致的确定性校验，再提交审核并发布不可变版本。

运行时将仓库内置案例和已发布案例合并。新发布案例可以参与路由、诊断、向导、步骤问答、作业卡和知识图谱，但已经创建的 CaseRun 继续使用创建时固化的版本和哈希。

### 3.8 第八阶段：实现资料驱动的多 Agent 案例生成

最后阶段在案例发布中心之上增加资料驱动的案例生成流水线。系统可以读取已入库手册、历史案例、知识图谱和现场数据快照，依次完成来源固化、文档理解、证据提取、故障领域判断、案例大纲、八模块生成、确定性校验、定向修复和 Patch 预览。

生成过程被拆分为可记录、可重试和可恢复的 Agent 任务。每项关键内容关联 EvidenceItem 和 JSON Pointer；没有证据的阈值、接线顺序、型号参数和安全操作不得直接补写。生成结果不能自动发布，必须经过专家确认大纲、选择性接受模块和既有案例发布流程。

系统已经提供散热、供电、存储、通信、监控、粉尘滤网、凝露和硬件等故障领域模板。默认使用离线结构化生成提供方，远程 JSON 模型通过环境变量注入，不在仓库保存凭据。

## 4. 最终形成的主要能力

### 4.1 工程师端

- 工程师登录、工作台和任务入口；
- 文字与语音异常描述；
- 图片、视频、音频、设备信息和运行参数接入；
- 历史案例、知识条目和厂商手册选择；
- 设备与故障确认；
- 具有依据的辅助诊断；
- 可编辑、可确认的检修预方案；
- 步骤化检修和检查结果记录；
- 当前步骤文字或语音追问；
- 语音播报与专家协同入口；
- 恢复运行验证；
- 检修记录和两页 A4 PDF 作业卡；
- 工程师知识图谱查看；
- CaseRun、revision、事件和快照管理。

### 4.2 专家端

- 待审核任务、历史案例和知识动态；
- 原始现场证据和工程师提交快照查看；
- 案例结论、知识条目和图谱关系修正；
- 退回补充、修正后通过和仅归档处理；
- 知识版本发布和应用验证；
- 全局知识图谱、本次新增修改、版本差异和局部子图；
- PDF 手册、页码、分块和证据检索；
- 案例草稿、确定性校验、审核、发布和历史版本激活；
- 资料驱动案例生成、大纲确认、生成轨迹和模块 Patch 审核。

### 4.3 管理与运维

- 用户、角色、组织、启停状态和密码管理；
- 会话过期、撤销、锁定和 token version；
- 业务审计和去敏导出；
- 检修工单和状态机；
- 手册批量入库与持久任务队列；
- 多来源统一证据检索及检索过程追溯；
- SQLite、外键、FTS、图谱摘要和运行资产一致性巡检；
- 完整运行资产备份；
- 存活、就绪、指标、请求追踪和 JSON 日志；
- systemd 服务、Nginx 配置和原生 Linux 部署脚本。

## 5. 当前真实技术实现

| 层次 | 当前实现 |
| --- | --- |
| 前端 | React 18、Vite 6、Lucide React |
| 后端 | Python、Flask 3、Gunicorn |
| 业务数据 | SQLite |
| 案例合同 | JSON、JSON Schema Draft 2020-12、SHA-256 |
| 知识检索 | SQLite FTS5、中文规范化回退、结构化 claim 检索 |
| 图谱 | SQLite 中的图谱版本、全量快照和增量关系 |
| 文档处理 | pypdf、PDF 分页提取和分块 |
| PDF 输出 | ReportLab |
| 文件 | 受限本地目录、文件大小限制和 SHA-256 |
| 部署 | 原生 Linux、Gunicorn、systemd、可选 Nginx |
| 测试 | Python unittest、Vite build、preflight、GitHub Actions |

目标架构文档中仍保留 Vue 3、FastAPI、PostgreSQL、pgvector、Neo4j 和千问模型等产品化选型，供未来重构参考。

## 8. 尚未完成或需要保留边界的内容

### 8.1 智能模型

- 默认诊断仍以案例规则和结构化知识为主；
- 案例生成默认使用离线结构化提供方；
- 远程 JSON 模型适配器已经实现，但需要部署方配置兼容服务和凭据；
- 真实图像识别和真实语音识别仍未作为最终代码能力验证；
- 前端已有多模态与语音交互入口，不应等同于真实识别服务已经接通。

### 8.2 工业数据

- 当前遥测来自工程师提交事实或演示数据；
- 工业协议网关通过 Provider 合同预留，需要部署环境实现；
- 不宣称已连接真实 PLC、SCADA、传感器或生产网络。

### 8.3 图谱和存储

- 当前图谱版本和关系持久化在 SQLite，并非 Neo4j 运行实例；
- 当前附件、手册和作业卡使用本地文件目录，并非对象存储；
- 单机部署具备备份恢复，但不提供集群高可用。

### 8.4 兼容与部署

- systemd、Nginx 和 LoongArch 脚本需要在银河麒麟目标机最终复核；
- 兼容旧演示接口时默认使用单 Gunicorn worker；
- 增加 worker 前需要完成旧状态迁移和压力测试。

## 9. Git 分支和归档说明

项目结束时建议按以下方式理解分支：

- `main`：最终归档和以后重新开始的默认入口；
- `submission/competition-platform`：比赛提交平台的完整开发历史；
- `Docs`：正式比赛文档和视频材料的编辑历史；
- `feature/industrial-computer-power-fault`：多故障及供电案例阶段历史；
- `feature/knowledge-graph`：知识图谱独立开发阶段历史。

本地 `run/`、`output/submission/`、`output/pdf/`、日志、数据库和压缩包不属于长期源码。它们可以由脚本、测试或打包流程重新生成。

## 10. 如果以后重新启动项目

建议按照以下顺序恢复：

1. 克隆 GitHub `main`；
2. 阅读根目录 `README.md`；
3. 阅读本文和 `Docs/competition-submission-feature-matrix.md`；
4. 阅读 `Docs/competition-submission-architecture.md`；
5. 阅读 `Docs/competition-submission-deployment-guide.md`；
6. 使用 Node 20、Python 3.10 或 3.12 执行 `make install`；
7. 执行 `make check`；
8. 使用本地结构化提供方启动，先验证散热和供电案例；
9. 再根据实际目标决定接远程模型、工业网关、向量检索或 Neo4j；
10. 新开发应从模块化案例平台和核心业务 API 继续，不回到前端硬编码方式。

## 11. 可继续复用的方向

如果未来还有比赛、课程设计、毕业设计或真实项目机会，现有成果可以沿以下方向复用：

1. 把案例发布和多 Agent 案例生成独立为工业知识生产平台；
2. 接入真实千问、OCR、ASR 和向量模型，替换本地结构化提供方；
3. 接入 PLC、SCADA、OPC UA 或其他工业协议网关；
4. 将 SQLite 图谱版本迁移至 Neo4j，并保留当前审核和版本合同；
5. 将本地文件存储迁移至对象存储；
6. 扩展到服务器、网络设备、PLC、仪表和其他工业装备；
7. 使用现有测试、部署和文档体系作为国产化软件交付模板；
8. 将检修记录和作业卡用于设备档案、培训和知识复盘。

## 12. 最终结论

项目已经从一个围绕散热异常的前端演示原型，发展为具备模块化案例、可追溯检修运行、专家审核、知识版本、图谱增量、手册证据检索、案例发布、多 Agent 案例生成和生产部署工程的单机平台。

它还不是可以直接进入生产网络的完整工业产品，真实模型、工业网关、目标机兼容和高可用仍需要继续投入。但仓库已经保留了清晰的业务闭环、可运行代码、结构化案例、知识资料、测试、部署脚本和完整文档，具备在未来项目中重新启用和继续扩展的价值。
